# 板端唤醒词误识别专项排查清单

日期：2026-04-02

## 1. 目的

这份文档只服务一个目标：

- 重新聚焦板端唤醒词误识别问题
- 把已经踩过的部署坑、调试坑、环境坑收拢起来
- 后续严格按分阶段计划排查，避免再把模型问题、板端前端问题、串口问题、云端问题和网络问题混在一起

本轮之后，默认不再把 TCP 调试链路作为主路径；主路径重新回到：

- 串口小日志
- `river kws debug local on`
- `river kws dump next/meta/chunk`
- host 侧 replay
- 训练侧 / TFLite / 板端三方对比

## 2. 当前问题状态总览

### 2.1 症状不是一直不变，已经经历了两个阶段

#### 阶段 A：不同语音输入，板端输出一度固定

在 2026-04-01 的一组日志里，出现了最典型的异常：

- 第一次真实唤醒：
  - `score_pm=375`
  - `q15=12288`
- 第二次误唤醒：
  - `score_pm=375`
  - `q15=12288`

也就是：

- 输入语音不同
- 触发场景不同
- 结果分数却完全一样

这说明当时的问题不能简单解释为“阈值太低”。如果正负样本都命中完全同一个输出值，更像是：

- 板端输入张量有问题
- 模型导出或量化有问题
- 板端输出读取 / 反量化有问题
- 或者模型在板端已经退化到一个极小动态范围

#### 阶段 B：加细日志和更新模型后，输出不再完全固定

到 2026-04-02，板端加入更细粒度日志后，已经看到明显不同的输出，例如：

- 一次高分命中：
  - `raw=116`
  - `score=0.953125`
  - `q15=31231`
  - `feat_hash=0x8d35339f`
  - `input_hash=0x796617ab`
- 一次较低但仍触发的命中：
  - `raw=56`
  - `score=0.718750`
  - `q15=23551`
  - `feat_hash=0xf34a27f0`
  - `input_hash=0xf70d324b`

这说明：

- 板端模型输出已经不是完全固定值
- 板端特征和输入张量哈希也在变化
- “板端推理完全卡死”这个结论现在已经不成立

### 2.2 当前更合理的结论

当前更像是下面三类问题之一，或者它们叠加：

- 板端前端与训练前端仍然未完全对齐
- 模型导出 / 量化 / 板端解释路径仍有偏差
- 板端分数已经恢复动态，但阈值和 hard negative 校准不够稳

## 3. 到目前为止，模型部署和板端调试踩过的坑

## 3.1 模型部署链路踩过的坑

### 3.1.1 旧模型量化 `MEAN` 路径不稳定

已经单独复盘过，见：

- [doc/KWS_MEAN_OPERATOR_POSTMORTEM_ZH.md](/root/ameba-river/doc/KWS_MEAN_OPERATOR_POSTMORTEM_ZH.md)

这条线暴露出的问题包括：

- `MEAN` reducer params 不稳定
- patched `MEAN` 对齐问题
- SDK 量化 `MEAN` scratch-buffer 路径崩溃

这类问题的结论是：

- 旧模型上的 `MEAN` 路径整体不可信
- 后续优先使用规避该路径的新模型，而不是继续修旧模型

### 3.1.2 导出格式一度不匹配板端 TFLite Micro

已经踩过的格式问题包括：

- 所谓“纯浮点导出”实际是 hybrid TFLite
- 板端不支持 hybrid 模型
- trainer 默认量化导出曾采用 `uint8` IO
- 当前板端 CA32 优化 kernel 更匹配 `int8` IO

这类问题的后果是：

- host 侧看模型正常
- 板端却无法稳定初始化或无法稳定运行

### 3.1.3 纯 FP32 虽然语义更直接，但板端内存预算不够

这条路已经验证过：

- 纯 FP32 模型在当前板端 arena / heap 预算下不可持续
- 回避量化问题不能靠“强行回 FP32”

### 3.1.4 CA32 优化 kernel 运行期也踩过坑

已经碰到过：

- `conv` 的 `im2col` 路径运行期崩溃

这意味着：

- 即使模型能初始化
- 也不代表板端运行时每一层都可靠

## 3.2 本轮板端唤醒词误识别相关踩坑

### 3.2.1 早期出现“输入不同，输出固定”

这类现象的风险最高，因为它会让排查方向严重偏向错误：

- 容易被误判成“就是阈值低”
- 但实际上更可能是导出、量化、输入张量或输出读取问题

### 3.2.2 后续又出现“输入不同，输出变化了，但误唤醒仍然存在”

这说明问题从“完全坏掉”演进为：

- 输出已恢复动态
- 但模型区分度、前端一致性、阈值策略仍未收敛

### 3.2.3 `same=[raw:..., feat:..., input:...]` 的语义还未彻底吃透

日志里出现过类似：

- `same=[raw:2 feat:1 input:1]`

这代表：

- 即使 `feat_hash` 和 `input_hash` 变了
- 最终 `raw` 仍可能重复

这提示两个方向：

- 模型输出动态范围仍偏小
- 或输出读取 / 量化映射存在压缩效应

### 3.2.4 云端 handoff 一度污染了 KWS 调试窗口

之前出现过：

- `Malloc failed. Core:[CA32], Task:[river_wake_evt]`
- `IPC Get Semaphore Timeout`

这会让：

- 唤醒命中后立即进入云端路径
- 拉低可用 heap
- 破坏后续 dump 和日志采集

所以当前默认做法必须是：

- 先 `river kws debug local on`
- 再做 KWS dump 和三方对比

## 3.3 实际串口调试踩过的坑

### 3.3.1 串口长日志过长，不适合人工复制

实际表现：

- 一旦打开较重的 diag，日志很快淹没关键信息
- 人工粘贴时容易截断
- 重要上下文丢失

### 3.3.2 monitor 交互层不稳定

实际表现包括：

- `Get cmd list expired`
- 命令注入和日志输出互相打断
- monitor 层本身会带来额外干扰

### 3.3.3 串口命令被拆断或与日志交错

出现过：

- `unknown command 'riv'`

这说明：

- 命令没被完整送达
- 或发送时正好被日志插入打断

### 3.3.4 原始串口抓取有时只拿到 `NUL` 或空输出

这类情况很危险，因为很容易误判成：

- 板子没有日志
- 板子没有跑到某一步

实际上可能只是：

- 抓取时机不对
- 设备节点状态不稳定
- monitor / flash / raw cat 多方争用串口

### 3.3.5 试图引入 TCP 调试后，问题被环境变量放大

已经确认的 TCP 侧坑包括：

- Windows 端口冲突
- WSL 和 Windows 的“可达性”语义不一致
- host 入站链路额外引入新变量

结论：

- TCP 调试这轮已经回退
- 不再作为主调试路径

## 4. 当前怀疑点清单

下面的怀疑点按“当前值得优先分析”的顺序排列。

## 4.1 怀疑点 A：板端前端与训练前端不一致

### 为什么怀疑

板端前端链路现在不是“训练脚本直接复刻”，而是：

- 双麦采集
- `fixed_dsb`
- log-mel
- global mean/std 归一化
- int8 量化后喂模型

这里任何一个环节和训练侧不一致，都会让：

- 正样本分数降低
- 负样本分数升高
- 或正负样本一起被压缩到狭窄区间

### 现有证据

支持这一怀疑点的证据：

- 早期出现过“输入不同，输出固定”
- 现在 `feat_hash` / `input_hash` 虽然变化，但误唤醒仍存在
- 板端存在 `pre-roll trim`、`queue dropped`、`input trim` 等窗口处理

削弱这一怀疑点的证据：

- 板端输出已经恢复动态，不像完全喂错 tensor

### 下一步检查

- 用板端 exact tensor dump 对比 host replay
- 用同一板端录音，对比训练侧特征与板端特征
- 重点核对：
  - DSB 输出
  - mel 维度
  - 帧数 `40x98`
  - 全局均值方差
  - int8 量化参数

### 退出机制

如果出现下面任意一个结果，就暂时退出这一怀疑点：

- board `input_raw` 与 host 根据同一 `feat_f32` 量化得到的结果一致
- training-side 特征与板端 `feat_f32` 基本重合

一旦这两点成立，就说明前端不是当前主矛盾，应转向阈值或模型区分度。

## 4.2 怀疑点 B：导出 / 量化 / 板端输出解释仍有偏差

### 为什么怀疑

前面已经反复踩过：

- hybrid / FP32 / uint8 / int8 的格式与部署错位
- runtime schema 与实际解析不一致
- 板端输出曾表现为固定值

### 现有证据

支持这一怀疑点的证据：

- 早期 `score_pm=375 q15=12288` 异常一致
- 后续即使 `feat_hash` 变化，`raw` 仍可能重复

削弱这一怀疑点的证据：

- 最新日志里 `raw=116` 和 `raw=56` 已明显不同
- 说明最终输出至少不是常量

### 下一步检查

- 直接拿板端 `input_raw` 做 host TFLite replay
- 对比：
  - host TFLite 输出 raw
  - 板端日志 raw
  - host 反量化后的 score / q15

### 退出机制

如果满足：

- 同一份 `input_raw`
- host TFLite raw 与板端 raw 完全一致

则基本可以退出“导出 / 板端输出解释错误”这一怀疑点。

## 4.3 怀疑点 C：窗口裁切 / pre-roll / gate / trim 影响了识别稳定性

### 为什么怀疑

日志里已经看到：

- `kws pre-roll trim`
- `kws gate open/close`
- `queue dropped`
- `kws input trim: dropped=17 queue=30->13`

这说明板端输入给模型的窗口并不是稳定、完整、固定的理想语音片段。

### 现有证据

支持这一怀疑点的证据：

- 不同触发样本中 `queue`、`trim_drop`、`pre_dropped` 变化明显
- 同一句话如果切窗不同，最终模型得分会飘

### 下一步检查

- 对误唤醒样本和真唤醒样本分别记录：
  - `gate open/close`
  - `queue peak`
  - `trim_drop`
  - `pre_dropped`
- 看高误检样本是否总伴随异常 trim / drop

### 退出机制

如果确认：

- 真阳性与误阳性样本在 trim/gate 指标上没有显著差异

则窗口链路不是第一优先级。

## 4.4 怀疑点 D：阈值与 hard negative 校准不够稳

### 为什么怀疑

当前阈值不是凭空推断，而是实际板端值：

- `threshold_q15=19660`

而误唤醒样本已经观察到：

- `q15=23551`

也就是误唤醒样本离阈值并不远，但已经跨过去了。

### 现有证据

支持这一怀疑点的证据：

- 输出已经恢复动态
- 误阳性样本仍能过线
- 当前怀疑更像“margin 不够”

削弱这一怀疑点的证据：

- 早期“固定输出”阶段不能只归咎阈值

### 下一步检查

- 收集一批板端真阳性 / 误阳性 / 近似负样本得分
- 画出最小统计：
  - 真阳性得分区间
  - 误阳性得分区间
  - 二者是否有可分 margin

### 退出机制

如果出现下面任一结论，就能临时退出“只调阈值”这条路：

- 真阳性和误阳性得分高度重叠
- 调高阈值会直接打掉大量真阳性

那就必须回去优先修前端一致性或模型 hard negative 训练。

## 4.5 怀疑点 E：板端 runtime 某一层仍存在实现偏差

### 为什么怀疑

虽然当前不再像 earlier `MEAN` 阶段那样明显 crash，但不能排除：

- 某一层 optimized kernel 行为与 host reference 不一致
- 最终只在输出上表现为分数异常

### 现有证据

支持这一怀疑点的证据：

- 平台侧之前已经踩过 kernel 级问题
- 如果 feature/input parity 全过，但输出仍不合理，就只能继续往层内看

### 下一步检查

- 只在必要时做 per-layer / per-op 中间张量 dump
- 首选关键点：
  - 第一个 conv 输出
  - 第一个 residual block 输出
  - 倒数第二层
  - 最终 logits / output tensor

### 退出机制

如果：

- feature parity 通过
- input parity 通过
- output parity 也通过

则完全退出这条怀疑点，不再做更深的层级 dump。

## 5. 分阶段分析计划

后续必须按阶段推进，每个阶段只回答一个问题。

## 5.1 阶段 0：冻结基线

目标：

- 不再引入新的 transport、AEC、实验 profile、云端联调变量

固定基线：

- 当前已回退 TCP 调试
- 保持单 AP Wi-Fi
- 使用本地 `kws debug local`
- 使用现有 pull-based dump 机制

退出条件：

- 仓库、板子、模型三者状态一致

## 5.2 阶段 1：先判断当前到底属于哪种症状

目标：

- 先判断现在还是不是“输入不同，输出固定”

做法：

- 连续抓多个真阳性和误阳性触发
- 只看：
  - `raw`
  - `score`
  - `q15`
  - `feat_hash`
  - `input_hash`

退出条件：

- 如果 `raw` 仍长期固定，回到“输出解释或输入量化异常”主线
- 如果 `raw` 已明显变化，转入后续 parity 与阈值主线

## 5.3 阶段 2：做 exact tensor parity

目标：

- 只回答“板端送进模型的 exact input，host replay 后输出是否一致”

做法：

- `river kws debug local on`
- `river kws dump next`
- 命中一次后拉取：
  - `meta`
  - `output_raw`
  - `input_raw`
  - `feat_f32`
- host 用同一模型 replay

退出条件：

- 如果 board output == host output，退出导出/输出解释怀疑点
- 如果不一致，优先修模型部署链路，不再碰阈值

## 5.4 阶段 3：做训练侧 / TFLite / 板端三方对比

目标：

- 只回答“训练侧特征和板端特征是否对齐”

做法：

- 从板端真实录音中拿一个样本
- 三方对比：
  - training-side feature
  - host TFLite feature/input
  - board dump feature/input

退出条件：

- 如果三方一致，前端主嫌疑降级
- 如果不一致，优先修前端链路，不再继续调阈值

## 5.5 阶段 4：收集分数分布并判断阈值是否可调

目标：

- 只回答“当前模型在板端是否具有足够 margin”

做法：

- 收集若干：
  - 真阳性
  - 易混淆负样本
  - 误唤醒样本
- 统计 `raw` / `q15`

退出条件：

- 如果有清晰 margin，才进入阈值推导
- 如果没有 clear margin，必须回训练 / hard negative

## 5.6 阶段 5：仅在必要时做中间层张量定位

目标：

- 只回答“如果 feature/input parity 都正常，第一处层内偏差出在哪”

做法：

- 按关键层做最小化中间张量 dump

退出条件：

- 一旦找到第一处分歧层，立即停止继续加更多层 dump
- 优先定位那一层的 kernel / quant / layout

## 6. 调试方式备选清单与退出机制

## 6.1 方式 A：串口小日志模式

用途：

- 快速看实时得分、哈希、gate/trim 指标

建议内容：

- 只保留一行 `kws diag`
- 少量 `kws status`

优点：

- 反馈最快
- 操作成本最低

风险：

- 容易被长日志淹没
- 命令和日志容易交错

退出机制：

- 如果连续两次出现日志不可复制、命令被拆断、输出不完整
- 立刻停止追加更多串口日志，转向 dump 方式

## 6.2 方式 B：pull-based tensor dump

用途：

- 获取一次准确的 `feat_f32` / `input_raw` / `output_raw`

优点：

- 精度最高
- 适合做 host replay 和训练侧对比

风险：

- 采集窗口有限
- 如果忘记 local debug，可能被云端 handoff 污染

退出机制：

- 如果连续两次 dump 过程被云端 / heap / IPC 干扰
- 必须先回到 `river kws debug local on` 的最小本地路径

## 6.3 方式 C：host TFLite replay

用途：

- 验证“板端 exact input -> host output”是否一致

优点：

- 不依赖串口长时间稳定
- 能直接把部署问题和阈值问题分开

风险：

- 前提是 dump 数据完整、格式正确

退出机制：

- 如果 board dump 不完整或 chunk 丢失
- 不继续解释 replay 结果，先修 dump 获取

## 6.4 方式 D：训练侧 / 板端录音三方对比

用途：

- 定位前端差异

优点：

- 最能回答“板端前端和训练前端是否一致”

风险：

- 依赖能拿到可信的板端录音
- 操作成本高于单纯看分数

退出机制：

- 如果录音源本身不可信或录制链路不稳定
- 暂停这条线，回到 exact tensor parity

## 6.5 方式 E：中间层张量 dump

用途：

- 定位 runtime 某一层是否偏了

优点：

- 一旦成功，定位最直接

风险：

- 侵入性最大
- 日志量暴涨
- 最容易再次踩串口坑

退出机制：

- 只有在 feature/input/output parity 都不能解释问题时才允许进入
- 一旦找到第一处分歧层，立即停止扩张 dump 范围

## 6.6 方式 F：板端分数分布采样

用途：

- 判断阈值是否还能调

优点：

- 能回答工程上最实际的问题：
  - 当前模型还能不能靠阈值收敛

风险：

- 如果前端和部署还没对齐，分布没有意义

退出机制：

- 若 parity 未通过，禁止做阈值结论

## 7. 当前推荐的执行顺序

后续推荐严格按照下面顺序执行：

1. 先确认现在是否仍存在“输入不同，输出固定”
2. 再做 exact tensor parity
3. 再做训练侧 / TFLite / 板端三方特征对比
4. 只有 parity 通过后，才看阈值与 hard negative
5. 只有前三步都解释不了，才进入中间层 dump

## 8. 当前最应避免的几个误区

- 不要一看到误唤醒就直接改阈值
- 不要在云端 handoff 开着时做 KWS dump
- 不要在串口已经不稳定时继续堆更多日志
- 不要在 exact tensor parity 未通过前讨论模型训练效果
- 不要重新引入 TCP 调试链路，把 transport 问题带回主线

## 9. 当前阶段的工作结论

到 2026-04-02 这个时点，最稳妥的判断是：

- “板端完全卡死，输出恒定”这个结论已经被新日志削弱
- 当前更像是：
  - 前端一致性
  - 模型导出 / 量化 / 板端解释
  - gate/trim 窗口处理
  - 阈值 / hard negative margin
  之间的组合问题

因此，后续不能再用“单一猜测”推进，而必须按本清单逐步排除。
