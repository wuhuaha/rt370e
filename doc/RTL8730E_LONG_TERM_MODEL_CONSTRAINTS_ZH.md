# RTL8730E 长期模型预研约束说明

日期：2026-04-03

## 1. 目的

这份文档面向算法侧的长期模型预研，回答四个问题：

- 这块 `RTL8730E` 板子的物理资源到底有多少
- 当前工程实际上已经用到了多少
- 哪些约束是当前软件策略，哪些约束是硬件或系统结构带来的长期约束
- 新模型在这个平台上应控制在什么级别，才更像是“可落地候选”而不是“实验室勉强跑通”

这里特别强调：

- **不能把当前工程里所有问题都当成长期硬瓶颈**
- 但也**不能只看芯片宣传资源，而忽略当前产品链路中的共享成本**

所以本文会把约束分成三层：

1. 物理上限
2. 当前工程的保守布局上限
3. 面向长期产品化的建议预算

## 2. 结论先说

如果算法现在要启动长期预研，我建议按下面这组约束来选型和筛模型。

### 2.1 平台大结论

- 这块板子的外部 DRAM/PSRAM **物理容量是 `64MB`**
- 当前工程**并没有吃满这 `64MB`**
- 当前项目为了降低风险，只用了一个**保守的 `12MB` 可见窗口**
- 在这个窗口里，当前主应用 `CA32` 只拿到了 **`8MB` carveout**
- 这 `8MB` 里，真正注册成 `CA32 FreeRTOS heap` 的只有 **`4.87MiB`**

换句话说：

- **长期预研不要把“当前只给 CA32 的 8MB”误当成芯片物理极限**
- 但在当前工程形态下，**新模型能否落地，仍然首先要服从这 `8MB CA32` 的现实**

### 2.2 面向新模型的建议预算

在**当前完整产品链路**下，也就是仍保留：

- `Wi-Fi`
- `fixed_dsb` 前端
- `Silero VAD`
- `KWS`
- `Xiaozhi realtime`
- `Opus`
- TTS 播放 / follow-up 会话

我建议算法预研先按下面的预算工作：

| 项目 | 建议值 | 可接受上限 | 超线含义 |
| --- | --- | --- | --- |
| 新模型新增 flash 占用 | `<= 1.0MiB` | `<= 1.5MiB` | 超过后会明显压缩当前 app 包演进空间 |
| 新模型新增运行时工作集（arena + scratch + 私有 buffer + 私有栈） | `<= 1.5MiB` | `<= 2.0MiB` | 超过后需要非常谨慎地验证碎片化与会话峰值 |
| 新模型新增运行时工作集的实验天花板 | - | `~2.5MiB` | 超过这个量级，应直接转入“扩布局/拆 profile”路线 |
| 模型初始化后系统 `heap_free` | `>= 1.5MiB` | `>= 1.0MiB` | 低于 `1.0MiB` 时，Wi-Fi/TTS/会话峰值风险明显上升 |
| 会话中的 `heap_min` | `>= 1.0MiB` | `>= 768KiB` | 低于此值时，后续叠加特性和堆碎片都危险 |

### 2.3 面向计算量的建议预算

当前长期模型如果要走“常驻在线产品链路”而不是“纯本地 demo profile”，建议把计算量控制在这个级别：

| 模型类型 | 建议计算预算 |
| --- | --- |
| 常开 VAD | 平均每 `16ms` 帧推理 `< 2ms`，上限不建议超过 `4ms` |
| 常开 KWS | 单次窗口推理 `< 20ms`，上限不建议超过 `40ms` |
| 本地小型命令词 / 意图模型 | 单核等效 `RTF <= 0.3`，放宽也尽量不要超过 `0.5` |
| 流式离线 ASR | 当前完整产品链路下不建议直接按主线 profile 落地，应单独评估更大 CA32 carveout 或专用 profile |

这里的核心原则不是“板子一定跑不到更大模型”，而是：

- **不要把 AP 两个核都默认当作可长期独占给模型**
- 模型必须给 `Wi-Fi`、音频 DMA、云链路、Opus、TTS 和任务调度留余量

## 3. 当前板级资源事实

## 3.1 CPU / 运行核事实

从当前启动日志和工程配置可以确认：

- `AP Freq 920 MHz`
- `NP Freq 230 MHz`
- `LP Freq 40 MHz`
- 应用主跑核是 **`Cortex-A32`**
- 当前工程构建使用：
  - `-mcpu=cortex-a32`
  - `-mfpu=neon`
  - `-mfloat-abi=hard`
- 当前 AP 侧为 **SMP 形态**
  - 运行日志出现 `smp: Bringing up secondary CPUs ...`
  - 运行日志出现 `CPU1: on`
  - 运行时统计同时出现 `IDLE0` 和 `IDLE1`
  - 当前配置里有 `CONFIG_CORE_NUM 2`

这对长期模型选型有两个直接影响：

1. **可以考虑利用 `NEON` 向量化能力**
2. **不能假设两个 A32 核都长期空闲给模型**

更实用的理解是：

- 这块板子适合做“中小型、流式、低时延”的端侧语音模型
- 不适合把 AP 当成“纯推理服务器”

## 3.2 Flash 事实

当前 boot log 已确认：

- `BOOT FROM NOR`
- Flash ID `c8-40-19`
- 容量 `256M-bit`

也就是：

- **物理 NOR flash = `32MB`**

但当前工程真正重要的不是物理 `32MB`，而是当前 profile 给应用包分了多少。

### 当前开发 profile

当前项目自定义开发 profile：

- app 包下载窗口：`0x08040000 ~ 0x08600000`
- 可用空间：`0x5C0000 = 6,029,312 bytes ≈ 5.75MiB`

### SDK stock profile

SDK 默认 app 包窗口：

- `0x08040000 ~ 0x08300000`
- 可用空间：`0x2C0000 = 2,883,584 bytes ≈ 2.75MiB`

### 当前镜像体积

当前构建产物：

- `km4_boot_all.bin = 51,872 bytes`
- `km0_km4_ca32_app.bin = 3,601,760 bytes`
- `ota_all.bin = 3,601,792 bytes`

所以：

- 在当前**开发单槽 profile** 下，还剩约 `2,427,552 bytes ≈ 2.32MiB`
- 在 **SDK stock / OTA 更接近的窗口** 下，当前镜像已经超出约 `718,176 bytes ≈ 0.69MiB`

这意味着长期模型预研必须分清两件事：

1. **在当前开发 profile 下能否装进去**
2. **未来若要恢复 OTA/双槽，是否还成立**

如果算法交付的新模型新增 flash 体积很大，那么：

- 即使今天开发版能烧进去
- 也不等于未来产品版 flash 方案仍然成立

## 3.3 外部 DRAM/PSRAM 事实

当前 boot log 已给出最关键的一句：

```text
PSRAM or DRAM End in layout is 0x60c00000, but actually is 0x64000000
```

这说明：

- 物理外部 DRAM/PSRAM 末尾：`0x64000000`
- 当前工程布局末尾：`0x60C00000`

从地址计算：

- 物理容量：`0x64000000 - 0x60000000 = 64MB`
- 当前工程可见窗口：`0x60C00000 - 0x60000000 = 12MB`

所以当前工程并不是“64MB 全开”，而是：

- **物理有 64MB**
- **当前只保守用了 12MB 窗口**

## 4. 当前工程的有效内存布局

当前 SDK 布局中，和长期模型最相关的几块如下：

| 区域 | 地址范围 | 大小 | 说明 |
| --- | --- | --- | --- |
| `KM4_BD_DRAM` | `0x60000020 ~ 0x6015B000` | `1387KiB` | KM4 主 DRAM |
| `CA32_BL3_DRAM_NS` | `0x60300000 ~ 0x60B00000` | `8MiB` | 当前 AP/CA32 主应用 carveout |
| `KM4_DRAM_HEAP_EXT` | `0x60B00000 ~ 0x60C00000` | `1MiB` | KM4 扩展 heap，当前仍保留 |
| 物理外部 DRAM/PSRAM | `0x60000000 ~ 0x64000000` | `64MiB` | 板端实际能力 |

这里最关键的是：

- **长期模型主跑空间是 `CA32_BL3_DRAM_NS` 这 `8MiB`**
- 不是整板 `64MB`
- 也不是当前 `12MB` 可见窗口里的全部空间

## 4.1 当前 CA32 静态占用和 heap

当前 `project_ap` map 里：

- `__psram_heap_buffer_size__ = 0x004DE000 = 5,103,616 bytes ≈ 4.87MiB`

而 `CA32_BL3_DRAM_NS` 总大小是 `8MiB = 8,388,608 bytes`

所以可以直接反推当前 `CA32` 静态占用：

- `8,388,608 - 5,103,616 = 3,284,992 bytes ≈ 3.13MiB`

这 `3.13MiB` 里包含：

- `.text`
- `.rodata`
- `.data`
- `.bss`
- `.stack`
- 页表 / 地址转换表
- nocache 区
- 其他静态段

因此当前 CA32 空间不是“8MiB 都能拿来放模型”，而是：

```text
CA32 carveout 8MiB
= 静态段约 3.13MiB
+ FreeRTOS heap 约 4.87MiB
```

## 4.2 KM4 侧也还占着外部内存能力

当前 `project_hp` map 里还能看到：

- `__psram_heap_buffer_size__ = 0x000F7320 = 1,012,512 bytes ≈ 0.97MiB`
- `__psram_heap_extend_size__ = 0x00100000 = 1,048,576 bytes = 1MiB`

这说明两件事：

1. 当前布局没有把所有扩展内存都送给 CA32
2. KM4 仍有自己的外部内存使用面

所以长期规划不能偷换概念成：

- “板子有 64MB，所以算法随便给个十几 MB 模型，后面一定能分出来”

## 5. 当前工程已经用掉了多少

## 5.1 当前完整链路的 CA32 heap 使用情况

从 2026-04-03 的板端日志可直接得到：

- `boot_ready heap_free = 3,813,568 bytes`
- 样例会话中的最低点约为 `heap_min = 3,522,048 bytes`

而当前 CA32 heap 总量是：

- `5,103,616 bytes`

因此当前完整链路下，CA32 heap 的**已使用动态内存**大约是：

- 启动稳定后：`5,103,616 - 3,813,568 = 1,290,048 bytes ≈ 1.23MiB`
- 会话低水位时：`5,103,616 - 3,522,048 = 1,581,568 bytes ≈ 1.51MiB`

这组数字很重要，因为它说明：

- 当前完整产品链路本身就会稳定吃掉 **`1.3 ~ 1.6MiB` 的 CA32 heap**
- 这是在**不额外上更大新模型**之前就已经存在的系统成本

## 5.2 当前语音模型路径本身的显式占用

从当前运行日志看：

- `Silero VAD`
  - arena 配置：`192KB`
  - 实测使用：`101,264 bytes`
- 当前 `KWS`
  - arena 配置：`688KB`
  - 实测使用：`586,128 bytes`
  - slack：`118,384 bytes`
  - 模型体积：约 `77,848 bytes`

当前 `KWS` 还会额外占用：

- `ctx ≈ 25KB`
- pre-buffer `≈ 10KB`
- queue `≈ 33KB`
- lazy dump `≈ 31KB`
- task stack `≈ 12KB`

所以现在这个完整链路已经证明：

- 板子能在 `Wi-Fi + 云链路 + Silero + FP32 KWS + 音频前后端` 共存下稳定启动
- 但这并不等于“后续模型可以无限继续放大”

### 如果新模型是“替换”而不是“叠加”

本文前面给出的“新增工作集预算”，默认是按下面这个假设写的：

- 当前完整链路基本保留
- 新模型要么是新增模块
- 要么虽然替换旧模块，但不会把旧模块占用完整回收给系统

如果未来新模型是明确替换当前模块，那么预算可以更灵活一些：

- 如果替换当前 `KWS`，可回收的大头大约就是：
  - `~586KB` 的 KWS arena 实占
  - 外加几十 KB 的 queue / ctx / stack / pre-buffer
- 如果替换当前 `Silero VAD`，还可以继续回收：
  - `~101KB` 的 VAD arena 实占

因此更准确的理解应是：

- **`1.5 ~ 2.0MiB` 是“在当前完整主线基础上给新模型留的保守新增预算”**
- **如果新模型本身就是下一代 KWS/VAD 的替代者，那么可用预算可以把被替换模块的工作集加回去**

但即使如此，我仍不建议算法按“账面空余 heap 全部归模型”来设计，因为：

- 最大连续块未知
- 会话峰值会波动
- 后续工程还会继续长大

## 5.3 当前算力表现给出的信号

当前板端日志里，FP32 KWS 反复出现：

- `kws infer slow: ... us=178215`
- 同量级数据多次复现

也就是：

- 当前这条 FP32 KWS 路径，单次推理大约在 **`178ms`**

这说明：

- 当前板上**已经能跑** FP32 模型
- 但这条路径对常开 KWS 来说**明显偏慢**

这个现象应该这样解读：

- **它证明了当前实现/模型组合还不够轻**
- **但不能直接推出“RTL8730E 长期就只能跑到 178ms”**

原因包括：

- 当前模型本身未必是最终结构
- 当前 TFLM kernel 路径未必是最优
- 当前项目还有大量系统并发
- 当前并未引入更激进的 `NEON` / kernel 优化

## 6. 哪些是硬约束，哪些不是

## 6.1 长期硬约束

下面这些约束，即使后面继续优化工程，也仍然要认真面对。

### 1. 主推理核是共享的 `CA32`

当前本地模型主跑核是 `CA32`，但它同时承担：

- 产品主应用
- 音频前后处理
- Wi-Fi / socket / websocket
- Opus
- 播放与会话状态机
- 各种任务调度与缓冲队列

所以长期模型不能按“裸机 benchmark”思路选型。

### 2. 当前板端推理路径受 cache / DMA 一致性约束

当前日志里 SDK 已明确警告：

- `Cortex-A32 will automaticly prefetch data to D-cache...`

这对长期模型的含义是：

- 音频 DMA、播放 buffer、模型前后处理共享内存时
- cache 行为不能忽略
- 大量额外 copy、频繁大块 cache maintenance、非连续 scratch 都会抬高系统代价

### 3. 大块连续内存比“总 free heap”更重要

当前我们掌握的是：

- `heap_free`
- `heap_min`

但模型真正是否能成功，很多时候还取决于：

- **最大连续可用块**

因此：

- 即使总 free bytes 看上去还够
- 也不代表一个大的 arena 一定能成功申请

这就是为什么本文给出的新增工作集预算会比“账面剩余 free heap”更保守。

### 4. Flash 窗口是产品化约束，不只是开发约束

物理 flash `32MB` 不代表 app 包就能随便变大。

如果未来恢复 OTA/双槽：

- 当前开发 profile 的 `5.75MiB` 应用空间并不能视作产品既成事实

## 6.2 当前不是长期硬瓶颈的项目

下面这些现象要重视，但**不应直接写进算法长期能力上限**。

### 1. 当前只开了 `12MB` 外部内存窗口

这只是当前工程为了稳定和验证面控制做的保守选择，不是芯片物理极限。

### 2. 当前 `CA32` 只拿到 `8MB carveout`

这同样是当前布局策略，不是物理死线。

### 3. 当前 `178ms` 级 FP32 KWS 延迟

这说明当前组合不够优，但不等于换模型、换 kernel、换布局后仍然只能如此。

### 4. 当前云链路 / websocket / uplink 拥塞

这属于系统软件策略和队列治理问题，不是“新模型一定会被它卡死”的硬件结论。

## 7. 对新模型的详细约束建议

## 7.1 如果目标是“常开唤醒 / 常开检测类模型”

这是当前板子最现实、最适合长期演进的一类模型。

### 建议约束

- 模型新增 flash：优先控制在 `512KiB ~ 1MiB`
- 新增 arena + scratch + 私有 buffer：优先控制在 `512KiB ~ 1.5MiB`
- 单次窗口推理：优先 `< 20ms`
- 绝对不要把 `> 40ms` 当作产品默认目标
- 尽量采用：
  - `Conv2D`
  - `DepthwiseConv2D`
  - `AveragePool`
  - `Add`
  - `Logistic`
  这一类静态图、卷积友好的算子

### 原因

- 这类模型适合持续运行
- 对 TFLM / 端侧 kernel 的适配成本可控
- 更容易吃到 `NEON` 或后续 kernel 优化收益

## 7.2 如果目标是“小型本地命令词 / 本地短句分类”

这类模型可以做，但建议按“可中断、可会话触发”的方式设计，而不是全天常开重模型。

### 建议约束

- 模型新增 flash：`<= 1.5MiB`
- 新增运行时工作集：优先 `<= 2.0MiB`
- 单核等效实时率：`RTF <= 0.3` 为佳，放宽也尽量不要超过 `0.5`
- 尽量设计成：
  - 流式增量推理
  - 固定 chunk
  - 静态 shape
  - 少分支、少动态分配

### 何时不该继续在主线 profile 里硬上

如果一个本地小模型已经需要：

- `> 2.0MiB` 工作集
- `> 0.5` 单核等效 RTF
- 或明显压缩 `Wi-Fi + TTS + follow-up` 余量

那就不应继续假设“它能直接并入当前主线产品形态”。

## 7.3 如果目标是“流式离线 ASR / 更大本地语音模型”

这个方向不是不能做，但不应把当前主线 profile 当成默认落点。

### 当前判断

在现有完整链路下，流式离线 ASR 级模型如果满足以下任一条件：

- 运行时工作集 `> 2.5MiB`
- 明显依赖更大的连续 arena
- 单核等效 `RTF > 0.5`
- 需要明显更多 flash 体积

则建议直接进入以下路线之一：

1. **更大的 CA32 carveout**
2. **本地优先专用 profile**
3. **切换更适合 A32 的 runtime / kernel 路径**
4. **把在线链路做成互斥或降级模式**

不建议的做法是：

- 继续硬塞进当前完整主线，然后靠“再抠几十 KB”赌稳定

## 8. 为什么本文推荐 `1.5MiB ~ 2.0MiB` 的新增工作集预算

这个建议不是拍脑袋，是从当前已知数据倒推出来的。

### 已知数据

- 当前 CA32 heap：`5.103MiB`
- 当前完整链路已占动态 heap：`1.23 ~ 1.51MiB`
- 当前完整链路空余 heap：`3.52 ~ 3.81MiB`

### 直接账面看起来

如果只看账面空余，似乎还能再塞 `3MiB+`。

### 但工程上不能这么算

因为还要考虑：

1. 后续代码继续增长
2. 会话峰值和边角分配
3. 堆碎片
4. 最大连续块未知
5. 将来可能新增：
   - AEC
   - 更多 beamforming / preproc
   - 本地 ASR side-path
   - 本地缓存 / 诊断

所以更稳妥的做法是：

- 先把 `1.0 ~ 1.5MiB` 留给系统余量和后续增长
- 把新模型的新增运行时工作集优先压在 `1.5MiB` 左右
- `2.0MiB` 以上就转为强验证项
- `2.5MiB` 以上就默认进入“当前布局不舒适”的区间

## 9. 算子与 runtime 选型建议

## 9.1 优先做“板端友好图”

当前项目的长期演进，优先级应是：

- 图结构先适配板端
- 再在这个约束内追求精度

这不是说精度不重要，而是说：

- **一个板端长期无法维护的图，最终也不是产品模型**

### 建议特征

- 固定 shape
- 流式输入
- 尽量少 op 种类
- 避免 custom op
- 避免需要频繁大块临时张量重排的结构
- 避免对 runtime resolver 提出过多新算子需求

## 9.2 关于 `MEAN` 的长期取舍

当前项目里，算法已经用其他算子替代了 `MEAN`。

从长期工程视角，我的判断是：

- **如果去掉 `MEAN` 后精度下降很小或可接受，优先保留“无 `MEAN`”板端友好图**
- **只有当去掉 `MEAN` 带来明确、稳定、不可接受的精度损失时，才值得单独投入做 `MEAN` 适配**

原因不是 `MEAN` 永远不能接，而是：

1. 板端支持更少算子，长期维护成本更低
2. 算子适配不仅是“编译过”问题，还包括：
   - tensor 语义正确性
   - cache / 对齐 / 性能
   - 后续版本回归
3. 如果算法侧已经能用等价结构消化掉 `MEAN`，通常这是更稳的产品路径

所以长期建议是：

- 先把“板端原生支持算子集合”作为算法搜索空间
- 再用实验数据决定某个缺失算子是否值得补

## 10. 对 KleidiAI / NEON 优化机会的判断

如果未来在这个工程里引入 `KleidiAI` 一类面向 Arm CPU 的 kernel 优化路径，我认为**有机会带来性能增益**，但要正确理解它的边界。

### 为什么可能有收益

因为当前主推理核是：

- `Cortex-A32`
- `NEON`
- hard-float

这意味着对于下面这类模型：

- 卷积主导
- depthwise + pointwise 主导
- GEMM/MLP 明显

只要 kernel 真正映射到 `NEON` 友好的实现，通常就有机会比当前通用实现更快。

### 但不要高估

`KleidiAI` 类优化不会自动解决这些问题：

- 模型 op 本身不适合当前 runtime
- 内存布局不够
- 大块 arena 申请失败
- 音频 / 云链路与模型并发抢占
- cache / DMA 一致性处理不当

### 更实用的结论

长期预研时，模型结构最好优先满足两件事：

1. **图本身板端可接**
2. **图的主算子是 `NEON` 容易优化的类型**

如果一个模型同时满足这两点，那么未来引入更强 CPU kernel 的收益就更有把握。

## 11. 建议算法侧采用的预研分层

为了不把当前工程状态和长期方向混在一起，我建议算法侧把模型预研按三层推进。

### A. 板端主线可落地候选

约束：

- 新增 flash `<= 1.0MiB`
- 新增工作集 `<= 1.5MiB`
- 常开 KWS `< 20ms`
- 单核等效 `RTF <= 0.3`

这类模型才适合作为近期产品候选。

### B. 需要系统优化但仍有希望并入主线

约束：

- 新增 flash `1.0 ~ 1.5MiB`
- 新增工作集 `1.5 ~ 2.0MiB`
- 常开 KWS `20 ~ 40ms`
- 或小型本地模型 `RTF 0.3 ~ 0.5`

这类模型可以做，但要配套：

- kernel 优化
- 内存碎片观测
- 更严的系统联调

### C. 明确需要新 profile / 新布局的研究项

特征：

- 新增工作集 `> 2.5MiB`
- 明显依赖更大连续块
- 对 flash 增量要求很大
- 明显需要更大 CA32 carveout
- 明显挤压云链路 / 音频主线

这类就不要再称为“当前主线直接候选”，而应明确标注为：

- **下一代本地化路线**
- **需要平台侧同步改布局 / 改 runtime / 改 profile**

## 12. 最后给算法侧的一句话版本

如果只保留一句话，我建议这样理解这块板子：

- **物理上，它不是只有 `8MB`，而是有 `64MB` 外部内存和 `32MB` flash**
- **工程上，当前真正给主模型使用的核心现实，是 `CA32 8MB carveout -> 4.87MiB heap`**
- **策略上，新模型最好先压在“新增 `1.5MiB` 级工作集、`1MiB` 级 flash、常开推理 `<20ms`”这个档位**
- **再大的模型不是不能做，而是应该从一开始就按“改布局 / 改 profile / 做系统级优化”立项**
