# RTL8730E 内存布局调整方案比较表

日期：2026-04-02

## 1. 目的

这份文档只回答一个问题：

- 当前这块 `RTL8730E` 开发板，是否建议调整内存布局，以更充分利用“板端物理 `64MB` DRAM”这项硬件能力

这里的讨论聚焦于：

- 当前 `ameba-river` 分支
- 当前 `CA32 + KM4 + KM0 + TrustZone + Wi-Fi + Audio + KWS/VAD/XiaoZhi` 运行形态
- 当前 SDK 级内存布局和 heap 组织方式

不讨论：

- 训练侧模型本身的识别质量问题
- 通过“只关模块、不改布局”得到的临时精简 profile

## 2. 结论先说

我的建议是：

- **中期战略上，建议调整内存布局**
- **短期解决当前模型是否可用的问题时，不建议把布局调整作为第一优先级**
- **如果要改，建议走“分阶段扩布局”路线，不建议直接一步拉满到 64MB**

原因很简单：

1. 当前固件明显没有吃满硬件内存能力
2. 调整布局可以直接增加 `CA32` 可用 heap，属于真实收益
3. 但当前新 `FP32` 模型的主要问题并不只是 heap，而是模型分数分布本身也有问题
4. 布局修改会牵涉 SDK、ATF、TrustZone、MPC、KM4 heap 分配边界，不属于低风险小改

所以正确姿势不是：

- “模型不好用 -> 立刻大改内存布局”

而是：

- “平台长期要承载更大本地模型 -> 把内存布局调整作为独立工程项推进”

## 3. 当前已知事实

### 3.1 物理内存比当前布局大

板端 boot log 已经明确提示：

```text
PSRAM or DRAM End in layout is 0x60800000, but actually is 0x64000000
```

这说明：

- 当前布局窗口末尾：`0x60800000`
- 硬件实际探测末尾：`0x64000000`

也就是：

- 物理内存能力约为 `64MB`
- 当前布局只按较小窗口在用

### 3.2 当前 CA32 carveout 只有 4MB

当前 SDK 布局文件中：

- `PSRAM_END = 0x60800000`
- `CA32_BL3_DRAM_NS = 0x60300000 ~ 0x60700000`

也就是当前主应用 `CA32` 的非安全 DRAM carveout 是 `4MB`。

见：

- `/root/ameba-rtos-1.2/component/soc/amebasmart/project/ameba_layout.ld`

### 3.3 当前 heap 来源就是这块 carveout 的尾部

`CA32` 链接脚本会先把这些内容放进 `CA32_BL3_DRAM_NS`：

- `.code`
- `.data`
- `.bss`
- `.heap`
- `.stack`
- `.nocache.data`
- `.xlat_table`

最后剩下的尾部导出为：

- `__psram_heap_buffer_start__`
- `__psram_heap_buffer_size__`

然后 `CA32` 用户堆配置直接把这块注册成 heap。

见：

- `/root/ameba-rtos-1.2/component/soc/amebasmart/project/project_ap/ld/ameba_img2_xip.ld`
- `/root/ameba-rtos-1.2/component/soc/usrcfg/amebasmart/include/ameba_userheapcfg_dram.h`

这意味着：

- **只要 `CA32_BL3_DRAM_NS` 做大，`CA32` heap 就会随之增大**

### 3.4 当前 KM4 也在占用扩展 heap 概念

SDK 的用户 heap 配置里，对 `CM4/KM4` 明确存在：

- `PSRAM_HEAP1_START = __psram_heap_extend_start__`
- `PSRAM_HEAP1_SIZE = __psram_heap_extend_size__`

这说明 `KM4_DRAM_HEAP_EXT` 不是完全没有语义的保留字段。

因此扩布局时不能简单理解为：

- “反正 KM4 不用，全部拿给 CA32”

## 4. 当前问题和内存布局的关系

需要特别强调：

- 内存布局调整可以解决“heap 不够”“arena 不够”“连续 DRAM 不够”
- 但**不能解决模型本身打分分布差、阈值不可分、识别质量不足**

以当前新 `FP32` 模型为例：

- 它的结构兼容性基本通过
- 但分数分布本身仍不理想
- 所以就算把 heap 放大，也不等于模型就能直接产品化

因此，对当前项目应做这样的优先级划分：

### 4.1 短期

用于回答：

- 当前某一版模型到底是“结构不兼容”还是“模型质量不够”

这时优先做：

- 模型结构/阈值/分数分布复核
- 板端实际 arena 测量

而不是先大改布局。

### 4.2 中期

用于回答：

- 平台之后是否要长期承载更大 `FP32` 模型
- 是否要承载更多本地推理模块
- 是否希望降低当前 `CA32 heap` 的长期风险

这时布局调整是合理且值得做的。

## 5. 为什么不建议一步拉满到 64MB

原因不是“技术上一定做不到”，而是：

- 风险和验证面会陡增

至少会牵涉这些层：

- SDK 布局文件
- `hal_platform.h` 常量
- ATF `NS_DRAM0_SIZE`
- TrustZone / MPC 安全区间
- CA32 FIP 保留区
- KM4 扩展 heap 和潜在依赖

一旦直接拉满，典型风险包括：

- secure / non-secure 边界定义错误
- BL2 / BL32 / BL33 装载区间和保留区冲突
- KM4 动态 heap 被意外挤压
- 某些依赖固定地址区间的模块出错
- 板端启动正常，但 Wi-Fi / Audio / IPC 在高负载下不稳定

所以更合理的路线是：

- 从“小步扩容、板端逐步验稳”开始

## 6. SDK 中已有的扩布局先例

SDK 自带的 `aivoice` 工具脚本里，针对 `RTL8730E` 已经存在一组扩布局 patch：

- `PSRAM_END`：`0x60800000 -> 0x61500000`
- `CA32_BL3_DRAM_NS`：`0x60300000 ~ 0x61400000`
- `KM4_DRAM_HEAP_EXT`：保留 `0x61400000 ~ 0x61500000`

见：

- `/root/ameba-rtos-1.2/component/aivoice/tools/patch_custom_cmd.py`

这说明：

- 扩布局并不是完全未经验证的空想
- SDK 团队自己也做过“扩大 CA32 可见 DRAM”的方向

但这不等于：

- 当前 `ameba-river` 分支就可以零风险照搬

因为我们当前工程负载组合、功能链路和验证目标并不等同于 `aivoice` 示例。

## 7. 方案比较表

下面给出几种现实可选的路线。

### 7.1 总览表

| 方案 | 核心改动 | 预期收益 | 风险等级 | 是否建议 |
| --- | --- | --- | --- | --- |
| A. 不改布局，只做模块精简 | 不改 SDK 内存布局，只关 VAD/云链路等 | 快速验证模型结构和阈值，不增加平台风险 | 低 | 适合短期问题定位 |
| B. 仅在当前 8MB 窗口内重分配 | 不扩 `PSRAM_END`，只在 `0x60000000~0x60800000` 内重分区 | 收益有限，通常只能挤出少量 CA32 空间 | 中 | 一般不优先 |
| C. 保守扩容 | 小幅提升 `PSRAM_END`，给 CA32 多增几 MB，同时保留 KM4 扩展区 | 能明显改善 CA32 heap，风险仍可控 | 中 | **推荐作为第一阶段** |
| D. 参考 aivoice 扩容 | 接近 SDK 现成 patch，把 CA32 提升到约 `17MB` | 收益大，足以缓解当前大部分 arena 压力 | 中高 | **推荐作为第二阶段候选** |
| E. 激进拉到接近 64MB | 大幅扩大窗口，尽量吃满硬件 | 理论收益最大 | 高 | 当前不建议直接做 |

### 7.2 各方案详情

#### 方案 A：不改布局，只做模块精简

**做法**

- 不改 SDK 布局
- 不改 `CA32_BL3_DRAM_NS`
- 通过关闭 VAD、云链路、播放缓存等做精简验证 profile

**优点**

- 见效最快
- 风险最低
- 适合回答“模型本身到底能不能跑”

**缺点**

- 不能提升平台长期能力
- 不能解决当前主线环境里的真实 heap 压力

**适用场景**

- 当前目标只是验证某一版模型的结构兼容性和粗略阈值

**退出机制**

- 如果模型在精简 profile 下仍表现差，说明问题主要不是内存布局

#### 方案 B：仅在当前 8MB 窗口内重分配

**做法**

- `PSRAM_END` 保持 `0x60800000`
- 尝试从 `KM4_DRAM_HEAP_EXT` 或其他区域里再挤一些给 `CA32`

**优点**

- 比扩窗口更保守

**缺点**

- 当前总窗口太小
- 能挤出来的收益有限
- 很可能不值得为这点收益承担验证成本

**适用场景**

- 只差很小一截内存即可满足目标

**结论**

- 对当前项目来说通常不是最优先路线

#### 方案 C：保守扩容

**做法**

- 在不接近 64MB 的前提下，先把 `PSRAM_END` 小步上调
- 同时扩大 `CA32_BL3_DRAM_NS`
- 但仍保留一定 `KM4_DRAM_HEAP_EXT`

**建议目标**

- 先把 `CA32` 有效可用 DRAM 从 `4MB` 提升到 `6MB ~ 10MB` 量级

**优点**

- 对 `CA32 heap` 的改善已经非常明显
- 风险比大幅扩布局低很多
- 板端验证周期可控

**缺点**

- 仍然需要改 SDK 和重新做 boot/runtime 稳定性验证

**适用场景**

- 平台准备长期承载更大 KWS/FP32 模型
- 但团队还不想一下子引入过大平台风险

**结论**

- **这是我最推荐的第一阶段方案**

#### 方案 D：参考 aivoice 扩容

**做法**

- 参考 SDK 里现成 patch
- 把 `PSRAM_END` 提升到 `0x61500000`
- 把 `CA32_BL3_DRAM_NS` 提升到约 `17MB`
- 给 `KM4_DRAM_HEAP_EXT` 仍留约 `1MB`

**优点**

- 收益非常明确
- SDK 内已有同方向先例
- 对 `FP32`、更大 arena、更复杂本地模块都更友好

**缺点**

- 风险面已经明显高于保守扩容
- 必须认真做：
  - boot 稳定性
  - Wi-Fi 稳定性
  - Audio 稳定性
  - 多轮唤醒/对话/播放压力验证

**适用场景**

- 确认平台会继续走更重的本地 AI 路线
- 愿意为平台能力做一次独立的 SDK 级改造验证

**结论**

- **适合作为第二阶段候选**

#### 方案 E：激进拉到接近 64MB

**做法**

- 尽量把硬件可见的 `64MB` 充分让 CA32 或非安全域使用

**优点**

- 理论空间最大

**缺点**

- 风险最高
- 很容易把问题从“内存不够”变成“平台边界不稳”
- 不是当前项目最需要的性价比方案

**结论**

- 当前不建议直接做

## 8. 我的推荐路径

### 8.1 推荐结论

我的推荐是：

1. **短期**
   - 不靠改布局去救当前模型质量问题
   - 先把模型结构、阈值、arena、分数分布问题看清楚

2. **中期第一阶段**
   - 做 `方案 C：保守扩容`

3. **中期第二阶段**
   - 如果确认平台长期走本地 AI 重载路线，再考虑 `方案 D：参考 aivoice 扩容`

### 8.2 不推荐的路径

当前不推荐：

- 直接做 `方案 E`
- 也不推荐为了当前某一版模型一时上板方便，就把布局调整和模型质量问题混在同一轮里推进

## 9. 各方案的验证重点

只要进入布局调整，最低限度都要验证：

1. 冷启动连续重启是否稳定
2. Wi-Fi 扫描、连接、重连是否稳定
3. XiaoZhi 会话建立/关闭是否稳定
4. 音频采集与播放是否稳定
5. KWS / VAD 启动是否稳定
6. `heap_free` / `heap_min` 是否显著改善
7. 是否出现新的 `Malloc failed` / IPC timeout / WLAN timeout

建议新增观测项：

- `boot_ready heap_free`
- `wifi_connected heap_free`
- `xSizeOfLargestFreeBlockInBytes`
- KWS `AllocateTensors()` 最小可通过 arena
- 多轮会话后的 `heap_min`

## 10. 每种路线的退出机制

### 10.1 方案 C 的退出机制

如果保守扩容后出现任一情况，应停止继续扩大并回滚：

- boot 链路不稳
- Wi-Fi 初始化/连接明显退化
- 音频链路或 IPC 出现新异常
- heap 没有获得符合预期的提升

### 10.2 方案 D 的退出机制

如果参考 `aivoice` patch 后：

- 平台稳定性明显下降
- 但 `CA32 heap` 提升又没有形成实际业务收益

则应退回方案 C，而不是继续激进扩容。

### 10.3 方案 E 的退出机制

当前建议直接不立项；只有在前两阶段都稳定、且确有明确需求时再重新评估。

## 11. 一句话总结

当前这块板子的 `64MB` 物理内存能力确实没有被现有布局充分利用，因此：

- **中期建议调整布局**

但从工程优先级和风险控制看，正确路线是：

- **先解决模型本身的质量与阈值问题**
- **再用分阶段扩布局的方式提升平台内存能力**

而不是：

- **把“模型当前不好用”和“平台长期内存布局优化”混成同一个问题一起硬推**
